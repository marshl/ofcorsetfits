# ofcorsetfits

A fit-finder for corsets. You enter your anatomical measurements (waist, underbust, upper hip, iliac); the app ranks every corset in its catalog by how well it will fit your body, then hands you a buy link at the size that fits best.

**Live:** [marshl.github.io/ofcorsetfits](https://marshl.github.io/ofcorsetfits/)

Inspired by [abrathatfits.com](https://www.abrathatfits.com/), which does the same thing for bras. Corset sizing is far more per-brand and per-style than bra sizing, so nothing similar existed for corsets.

## How it works

Each corset in the catalog is described by its **spring profile** — the difference between its waist circumference and its circumference at other landmarks (rib, upper hip, low hip), plus how far below/above the waist those landmarks sit. Your body is modelled the same way: a landmark set with a circumference and a signed position relative to your natural waist.

For every `(silhouette × stretch class × available size)` combination in the catalog, a scoring pass computes a per-landmark penalty and sums to a total. Lower is better; the ranked list shows results grouped into score tiers so ties are visible at a glance.

The scoring engine (`src/scoring/`) is a pure TypeScript library with no framework dependencies — all UI is built on top of it, and its behavior is covered by 29 tests.

**Key scoring knobs** (defaults):

- **Waist target** — corsets are ranked against `natural_waist_in - desired_reduction_in`, not against your natural waist. Corsets are usually worn cinched.
- **Non-waist asymmetry** — a corset that runs LOOSE at a rib/hip landmark (floats over the body, doesn't contour) is penalized more heavily than one that runs TIGHT (closes small and just leaves a wider lacing gap there, which is largely cosmetic).
- **Stretch class** — every catalog variant carries a `low / medium / high` stretch class that adds a slack allowance to the effective waist. Filterable in the UI.
- **Acceptable gap shapes** — you check off which lacing-gap shapes you'd wear: curved `)(` (natural corset curve — pinches at the waist), parallel `||` (uniform gap), slanted `/\` and `\/` (wider at hip or rib), or fully closed `|`. Each corset is scored under every shape you accept and takes its best. The winning shape is shown on each result row.

Full design notes live in the design doc kept out-of-repo; the code is meant to read cleanly on its own.

## Local development

```bash
npm install
npm run dev        # serves at http://localhost:5173/ofcorsetfits/
npm test           # runs the scoring engine tests
npm run build      # writes dist/
npm run preview    # serves the built dist/
npm run typecheck
```

The catalog file (`catalog/mystic-city.json`) is imported statically, so the entire app is a single `dist/` folder with no runtime dependencies. That's what gets published to GitHub Pages by the `.github/workflows/deploy.yml` workflow on every push to `main`.

## Refreshing the catalog

The catalog isn't hand-edited. It's generated by a Python pipeline that fetches data from each vendor's public site. See [`catalog/README.md`](catalog/README.md) for the full flow — the short version:

```bash
python3 catalog/vendors/mysticcity/refresh.py
```

That runs eight steps end-to-end: sitemap → comparison chart → URL matching → per-page metadata → interactive hip-position review → build v1 → per-variant size fetch → build v2. Each vendor lives in its own folder under `catalog/vendors/`; shared helpers (rate-limited HTTP, WooCommerce dropdown parsing, sitemap URL extraction, stretch-class inference) live under `catalog/vendors/shared/`.

The interactive step prints each product URL and asks you to open it in a browser and read the hip positions off the size-chart image — those positions aren't machine-readable from HTML. Entries save incrementally so Ctrl-C is safe. `--assume-defaults` skips the prompt for CI-style runs.

Currently-wired vendors:

- [Mystic City Corsets](https://mysticcitycorsets.com/) — WooCommerce. Catalog data comes from MCC's `ninja_tables` ajax endpoint (whole-catalog spring/geometry) plus per-variant product-page scrapes.
- [Timeless Trends](https://timeless-trends.com/) — Shopify. Catalog data comes from `/collections/all/products.json` (bulk product enumeration) plus per-silhouette sizing-info pages (`/pages/*-sizing-information`) for the spring numbers.

Adding another vendor is a matter of copying `catalog/vendors/<existing>/`, adjusting the fetchers to the vendor's platform (`shared/woocommerce.py` and `shared/shopify.py` cover the two big ones), and writing a new output `catalog/<vendor>.json`. The scoring engine doesn't care where a catalog came from.

## Data + ethics

Everything in the catalog is factual: measurements, sizes, materials — factual data isn't copyrightable in most jurisdictions. Vendor `robots.txt` files are respected, requests are rate-limited (≥2 s apart), and the fetcher's `User-Agent` identifies the project and a contact address.

The tool this data feeds is a fit-finder that drives clicks toward buying corsets from the vendor — aligned with vendors' interests, not competing with them. If any vendor ever objects, the recovery path is: remove the raw data for that vendor and refactor to fetch on the fly from their public endpoints at page-load time.

## Repo layout

```
src/
├── scoring/                 # framework-free TypeScript scoring engine
│   ├── types.ts             # Body, Catalog, ScoringConfig, RankedResult, ...

│   └── ranking.ts           # rank() — one row per (variant group × size)
└── ui/                      # React app
    ├── App.tsx              # state + live ranking

    ├── RankedList.tsx       # right-hand ranked list with tiered rows

    └── styles.css

```
